* Disc lifecycle: rip, library, metadata, playback

Bring ripped DVD/Blu-ray dumps up to the same first-class status Loku already
gives yt-dlp libraries: friendly titles and rich metadata instead of a flat
bucket of mangled filenames.

Governing principle: Loku owns the media lifecycle end to end — input (ripping),
library (organization and metadata), format (keeping serviceable
representations), and its own playback.  This is a deliberate consolidation, not
a set of Unix-style single-purpose tools wired together with systemd.  The merit
is the guarantee: rip, format, and metadata are one bound concern — consistency
has to hold from the moment a disc is ripped through to the moment it plays — so
one system that controls all of them can promise every library item is
serviceable end to end, which wired-together stages can only hope for.  The
spine of that guarantee is a Kodi-compatible =.nfo= sidecar per video, generated
from an authoritative TMDB identity, so the metadata is written once and read by
everything.

Design rationale is kept inline throughout so it is not re-derived later.

The downloads dataset follows the same governing principle in its own tree — see
"Downloads lifecycle (replace metube)".

** Scope and boundaries — what Loku does not do

Loku deliberately does not replace Kodi.  Kodi's job is playing to a *specific
device* — the living-room TV, a set-top box — and that stays Kodi's.  Loku
governs the pipeline and serves its own network/browser playback; the two
coexist rather than compete.

That coexistence is the whole reason the NFO and library layout stay
Kodi-compatible: Loku and Kodi meet at one shared artifact — the authoritative
library plus its sidecars — and Kodi keeps working as the device front-end by
reading exactly what Loku produces.  The rule that falls out: if a feature only
makes sense as "Loku playing to a dedicated device," it is out of scope.  That
is Kodi's side of the boundary, not Loku's.

** Consume NFO sidecars

*** DONE Parse Kodi =.nfo= sidecar files

=.nfo= is XML despite the extension.  There is no formal schema — different
generators (Kodi, tinyMediaManager, FileBot, Sonarr/Radarr) emit different
subsets — so parse liberally, not strictly.

- Branch on the root element: =<movie>=, =<episodedetails>=, =<tvshow>=.
- Model nearly every field as optional or repeated (=Option=, =Vec=); tags such
  as =<genre>=, =<actor>=, =<uniqueid>= legitimately repeat.
- Tolerate real-world mess: stray HTML entities in =<plot>=, BOMs, mixed
  encodings, occasionally invalid XML.
- Tolerate the degenerate foreign case where the whole "NFO" is a single bare
  URL or IMDb/TMDB id rather than XML.  Loku only needs this for NFOs written by
  *other* tools; ones Loku writes follow the canonical subset below.
- Use a forgiving deserializer (=quick-xml= + =serde=).  Name the type =Nfo=
  (Pascal initialism), not =NFO=.

*** DONE Mirror Kodi's NFO lookup rules

So Loku and Kodi agree on which sidecar belongs to which video:

- =Movie.mkv= → =Movie.nfo= (same basename), else =movie.nfo= in the folder.
- Episodes → =Episode.nfo= beside the file; series-level data in =tvshow.nfo= at
  the show-folder level.

*** DONE Surface NFO metadata in the browse/search UI

Friendly titles and metadata should flow into the existing index and full-text
search the same way yt-dlp =info.json= data does today.  This is the actual
user-facing payoff — the "big bucket of videos" problem the whole effort exists
to fix.

Landed: NFO titles, years, genres, and plots flow through the SQLite index into
browse, cross-library full-text search, and the player metadata panel.  Rips
without an NFO get a cleaned filename title (marked as such via =title_source=,
so the UI can style guessed titles differently) and an extracted thumbnail
frame.

*** DONE Key disc sets on the per-disc directory, not the filename prefix

=disc.rs= groups a set by the filename prefix ahead of =_tNN=, which fits
MakeMKV's Blu-ray basenames (=title_t00=) but not its DVD ones: those carry a
per-title token from the on-disc structure (=C3_t00=, =D2_t04=), so every DVD
title indexes as its own one-file set.  Under the per-disc directory layout (see
"Rip each disc into its own directory") the set /is/ the directory.  Keep the
prefix heuristic only for legacy flat rips, and even there treat a shared label
as a hint rather than proof of one disc — see the backlog note.

Landed: a directory carrying a =disc.json= manifest is one disc set; the scanner
records it in a =discs= table (label, id, fingerprint, and the identity read
back from a directory-level NFO), every title inside keys its set on the
directory, and the browse API renders the directory as one card with the
resolved title, year, and poster.  Hidden directories are pruned from the scan
and the watcher so rip staging never surfaces.  The prefix heuristic remains for
legacy flat rips only.

** Produce NFO sidecars (fold ripping into Loku)

The decision is that Loku owns the rip, so it is the ultimate consumer and
producer: rip, resolve identity, write NFO + artwork, done.  This replaces the
standalone =nixos-modules/makemkv-ripper.nix= service in ~/dev/nix-config over
time.

*** DONE Own the rip pipeline (invoke =makemkvcon=)

Absorb the ripping the NixOS module does today: scan the disc, rip *all* titles
(=makemkvcon mkv ... all=), name and place the output.  Policy is "rip the whole
disc — the disc becomes the offline backup, the rip is authoritative."  Ripping
everything (not main-title-only) is what keeps our captured structure matched to
how TheDiscDB catalogs discs.

Landed: the server polls the drive through =udevadm= (no udev rules, no trigger
route), scans with =makemkvcon --robot info=, rips every title into hidden
staging inside the discs library, verifies the title count, and swaps the
directory into place; the compat worker is woken directly.  Missing tools
degrade the =rip= health component rather than the server.

*** DONE Persist the =makemkvcon -r info= output as a first-class artifact

This is the key fix.  =makemkvcon -r info= emits the structured =TINFO=/=CINFO=
disc analysis — the exact data TheDiscDB stores and the matching key we need.
The current NixOS module *generates* it but writes it to a temp dir that is =rm
-rf='d on success (surfaced to the journal only on *failure*), so it is thrown
away for every rip that worked.

Capture it at scan time and store it in the per-disc directory (next task).  It
costs nothing at rip time; reconstructing it afterward is lossy or requires
re-scanning the disc.

Landed: =disc-info.txt= holds the raw dump and =disc.json= the parsed title
table, udev facts, disc id, and structural fingerprint.

*** DONE Rip each disc into its own directory keyed by label plus a disc id

The obvious output name — disc label plus MakeMKV title index, which the NixOS
module uses today — collides inside box sets.  Every disc of a season set can
carry the same volume label and the same title layout, so the second disc
silently replaces the first.  This has already destroyed rips: the first discs
of Voltron: Legendary Defender seasons one and two, and the Chamber of Secrets
feature, replaced by its own bonus disc.  A same-shaped overwrite leaves no
trace at all.

Rip into =<label>__<id>/= where =<id>= is unique per pressing and identical on
every re-insert of the same disc, so the directory doubles as the "already
ripped" check.  The preferred source is the disc filesystem's UUID as udev and
=blkid= report it (=ID_FS_UUID=: the volume creation timestamp for ISO 9660, the
volume set identifier for UDF).  It is readable before the slow MakeMKV scan and
does not drift with MakeMKV versions.  Fall back to a hash of the =makemkvcon -r
info= title lines, then to a rip timestamp; no step of the fallback chain may
yield a directory that already exists.

The id is a directory handle, not a matching key: TheDiscDB matching still runs
on the structural fingerprint below, computed from the info dump persisted
inside the directory.  Once identity resolves, rename to =<Title (Year)>__<id>/=
so the tree is discoverable by name.  The suffix is what makes the rename safe,
and the NFO, not the directory name, stays the authority Kodi reads.

Persist beside the MKVs: the info dump, and the udev/=blkid= facts captured at
rip time (label, UUID, volume set id, application id).

Landed as described: udev UUID, then a hash of the =TINFO= lines, then a
timestamp (which the policy refuses to reuse).  The rename to =<Title
(Year)>__<id>= is the identity resolver's job.

*** DONE Re-insert policy: skip, rescan, or rerip

Default =skip=: a directory for this id exists, do nothing.  =rescan= refreshes
only the sidecars via =makemkvcon -r info=, a matter of seconds, which is the
common need while the metadata pipeline is still maturing.  =rerip= stages the
whole rip into a temporary directory and swaps it in only on success.  No mode
overwrites in place, deliberately or otherwise.

Landed: =rerip= moves the previous tree to =.rip/replaced/<dir>__<ts>/= and a
failed attempt's staging to =.rip/failed/=; a daily in-process sweep deletes
both once older than =replaced_retention_days=.  =POST /api/rips= overrides the
configured policy for the disc in the drive.

*** DONE Optional attended identity confirmation at rip time

When the disc is in the drive we know the most.  Offer an attended path: run the
TMDB search, show the top few candidates, let the operator pick (or auto-accept
a confident single match).  Resolve to a TMDB id *once*, as early as possible,
and key everything off the id afterward.  Headless rips fall through to the
resolver chain below.

Landed: every rip is handed to the identity worker as soon as it is indexed;
what the chain cannot settle waits in the Rips page's "Needs identification"
list with the top candidates, a free-text re-search, and a one-click pick
(=/api/discs/unresolved=, =/api/discs/{library}/identify=,
=/api/discs/{library}/identity=).  The pick is keyed off the TMDB id from then
on.

** Format and compatibility governance

Owning the lifecycle means guaranteeing every library item is actually playable,
without ever degrading the archival master.  This is the scope the "Loku governs
everything" decision pulls in, and the part most likely to balloon — bound it
deliberately.

*** DONE Settle the format policy: master vs. playback representations

The full-quality whole-disc MKV is the archival *master* and the source Kodi
plays to devices — it is never the thing degraded.  Loku's own in-browser
playback has narrower codec/container support than a Kodi device, so it may need
a browser-friendly representation.

Open question to settle before building, since it sets the storage/latency/CPU
trade-off for the whole system: does Loku (a) produce a derived encode kept
alongside the master, (b) remux on demand, or (c) transcode on the fly at stream
time?  Whatever the answer, derived representations are *additive* — the master
is authoritative and untouched.

Decision: (a), an eager derived copy kept alongside the master.  A serial
in-process worker produces =foo.compat.mp4= beside each master lacking a
browser-playable representation — stream-copying browser-safe H.264 (the Blu-ray
fast path: no CPU-hours, no quality loss), transcoding otherwise with
deinterlacing for interlaced DVD sources, audio to AAC, faststart for immediate
seek.  Eager rather than on-demand or live because the governing principle
demands Loku /verify/ every item is serviceable up front: failures surface at
ingest time in the index, not at play time in someone's evening.  Derived copies
write beside masters via a =.part= rename, so they are Kodi-visible artifacts
(excluded from its scan), restic-excludable, and rebuildable at will; the master
is never modified.

*** DONE Track per-item playback compatibility

Loku should know, per library item, whether a directly-playable representation
exists for its browser player.  Surface incompatible items explicitly rather
than failing silently, and drive whichever derivation policy the task above
settles on.

The player-source strategy this builds on is now settled and implemented: the
browse API derives a =native_type= per video — the exact =<source type>= string
with an RFC 6381 codecs parameter (e.g. =video/mp4; codecs="av01.0.05M.08,
opus"=), taken from the =info.json= =vcodec=/=acodec= fields.  That codecs
parameter is what makes a browser's =canPlayType= authoritative: an incapable
browser rejects an undecodable native (AV1/VP9/Opus) up front and drops to the
compat copy without downloading it, while a capable browser plays the native at
full quality.  A non-standard container (MKV/AVI/MOV) or unknown codec yields no
=native_type=, so the player serves only the compat copy.  This replaced the
earlier container-MIME-plus-=canWebm=-ordering heuristic, which could not
discriminate codecs and so let Safari download an entire incompatible file
before falling back.

Remaining for this item: expose the compatibility fact in the browse/search UI
(the "surface incompatible items explicitly" half), and — the real gap, since
=native_type= only describes what already exists — guarantee a compat copy is
present, which depends on the derivation policy above and on whatever produces
=.compat.mp4= today (an external pipeline).  An =info.json=-less item (e.g. a
ripped disc) has unknown codecs, so it currently degrades to compat-or-bust; an
=ffprobe= fallback would recover =native_type= for those.

All three gaps are now closed: the =ffprobe= fallback fills codec facts for
=info.json=-less items (cached per content), the in-process derivation worker
guarantees the compat copy, and every API item carries a computed =derivation=
status (=not_needed= / =done= / =processing= / =pending= / =failed= / =unknown=)
that the UI surfaces as badges on cards and as an honest "being prepared" panel
in the player instead of a doomed playback attempt.

An end-to-end test of the actual browser selection needs a real Safari, which is
impractical in CI; the server-side contract it rests on (byte-range serving,
per-codec =native_type= derivation) is covered by headless integration tests
instead.

** Resolve identity (disc → TMDB id)

The disc never carries the friendly metadata; only weak identity hints.  Resolve
those to a TMDB id, then pull metadata from TMDB.  TheDiscDB provides the
disc-structure → title bridge that TMDB itself does not.

*** DONE Compute a structural fingerprint from MakeMKV =TINFO=

Fingerprint the *disc structure*, never the output MKV (the MKV is a derived
artifact and varies by ripper/version/settings, so it is useless as a shared
key).  The structural fields — per-title duration, size, segment map, chapter
count — are read off the disc and are deterministic per pressing.

Crucially this is *uniform across DVD and Blu-ray*: MakeMKV normalizes both
=VIDEO_TS= and =BDMV= into the same title model, so we sit on that abstraction
rather than the format-specific on-disc structures.

Landed: SHA-256 over the sorted (duration, chapter count) pairs of titles of ten
minutes or more, versioned in the preimage, stored in =disc.json= and the
=discs= table.  Fewer than two substantial titles is a weak fingerprint: a cache
hit on one is a suggestion, not proof.

*** TODO Match against a local TheDiscDB mirror

TheDiscDB stores raw =makemkvcon= logs plus a summary mapping and
=release.json=; it is a dataset (mirror the files locally), not a live query
API, and it does no matching itself — that is ours to build.

- Match on the *multiset* of (duration, chapter count) across the substantial
  titles.  Treat size as a weaker/fuzzy signal.
- Be tolerant of the short-title fringe: MakeMKV version heuristics and the
  minimum-title-length setting change *which short/decoy titles appear*, but not
  the durations/segment maps of the real ones.  Keying on the meaty titles
  designs that drift out.  (Note: this version-drift risk is our concern as the
  matcher author — TheDiscDB does not acknowledge or handle it.)
- Low-entropy discs (a single title, no extras) carry too little structure to
  match confidently.  Send those to the fallback rather than trusting a match.

*** DONE Implement the resolver chain

Ordered strategies, each returning an optional TMDB id; cheap deterministic
layers first, interactive last:

1. TheDiscDB structural match.
2. GTIN (barcode) lookup — see below.
3. Clean title from Blu-ray =BDMV/META/DL/bdmt_*.xml= or the DVD volume label →
   TMDB text search, auto-accept a confident single match.
4. Human / LLM "pick one of these candidates" fallback for the tail.

Landed: strategies 3 and 4 (the cache, the TMDB text search with a strict
auto-accept, and the attended pick) behind a =Strategy= seam; TheDiscDB and GTIN
slot in ahead of the search under their own entries.

*** TODO Model the barcode as a GTIN, not a "UPC"

The barcode is a globally unique edition key (GS1 hierarchical prefix allocation
guarantees no cross-border collisions), but it lives on the *packaging*, not the
disc — so it needs a scan or manual-entry step, and only ever *disambiguates*;
it does not resolve to metadata by itself.

- Store the full GTIN-13; normalize a 12-digit UPC-A up by left-padding a =0=.
  Never assume 12 digits — this is exactly what would break Japanese titles,
  which carry 13-digit JAN/EAN-13 codes (GS1 prefixes =45=/=49=).
- Name the field/type =Gtin= (Pascal initialism).  TheDiscDB calls its field
  "UPC" colloquially; feed it the GTIN-13.

*** DONE Cache =fingerprint → tmdb_id= and backfill on miss

A one-table SQLite cache, seeded from TheDiscDB where it has coverage.  Hit →
instant.  Miss → run the resolver chain, then write the result back so the next
encounter of that exact pressing is free.  A fingerprint identifies "this exact
disc," so a *different* pressing of a known title is a fresh miss (then cached)
— inherent to disc-identity keys and acceptable.

Landed as =identity.db= in the state directory — its own file, so the media
index's drop-and-rescan policy cannot wipe it.  TheDiscDB seeding is still open
under "Match against a local TheDiscDB mirror".

*** DONE TMDB client and NFO/artwork writer

- Resolve by id (=/find= external-id or a direct id lookup) for exact matches,
  and by =/search= for the bootstrap step.
- Serialize the returned JSON into the canonical NFO subset plus downloaded
  artwork.  The reader and writer share one schema, so Loku's parser only has to
  be bulletproof against *foreign* NFOs.
- Japanese titles: query with =language=ja= (and keep original-language fields).
  For anime specifically, AniDB / TheTVDB often map episodes better than TMDB —
  evaluate when we get there.

Landed: =/search/movie= + =/search/tv= (multi-search accepts no year and returns
people), =/movie= and =/tv= with credits, certifications, and external ids,
posters and fanart, and =tmdb_language= for the Japanese case.  A TV disc gets a
show-level =tvshow.nfo=; per-episode mapping is its own entry below.

*** TODO Per-episode NFO mapping for TV discs

A series disc resolves to the show and gets =tvshow.nfo=, but its titles are not
mapped to episodes, so Kodi sees a show folder with unnamed files.  Mapping
needs title-to-episode matching (durations and order against TMDB's season
listing, or TheDiscDB's summaries where they exist); the season and disc number
the label already yields are the starting point.

*** TODO Re-seed the identity cache from NFOs during scans

The cache only accelerates the next encounter of a pressing; if it is lost,
every resolved disc still carries its identity in its NFO and its fingerprint in
=disc.json=.  A scan pass that writes those pairs back into the cache would make
it fully rebuildable.

*** TODO Auto-identify legacy flat rips

The identity worker only sees =disc.json= directories.  The pre-Loku backlog
(flat =<label>_<title_tNN>.mkv= files) has no manifest and so never enters the
queue; see the backlog section for the options.

** Backlog (already-ripped discs)

Filenames cannot be trusted to delimit discs in the backlog.  Same-label box
sets overwrote one another under the flat layout, so a label's surviving files
can be the last disc plus stragglers from earlier ones.  A title index whose
mtime predates lower indexes under the same label is the only visible tell; a
same-shaped overwrite leaves none.  Inventory the backlog by content — title
cards, frame sheets, or the structural fingerprint against a fresh disc scan —
not by name.

The existing rips discarded their =disc-info= logs (deleted on success), so the
journal *cannot* be scraped to reconstruct TheDiscDB-format logs.  Options, none
requiring a full re-rip:

*** TODO Decide backlog strategy: re-scan vs. probe vs. one-time resolve

- Re-scan: =makemkvcon -r info= per disc regenerates the exact log in seconds
  (needs the disc, which the cold-backup policy means we still have).
- Probe existing MKVs: =ffprobe= / =mkvmerge -i= yields per-title duration and
  chapter count with no disc handling, but size and segment maps are lost, so
  the signature is weaker.
- One-time title resolution (filename/volume-label → TMDB with a human/LLM
  confirm) may simply be the least work, since the backlog is a bounded,
  eyeballed job anyway.  Reserve the structural-fingerprint path for go-forward
  automation, where the no-interaction payoff actually lands.

* Downloads lifecycle (replace metube)

The same governing principle as the disc tree, applied to the other dataset:
Loku owns the download lifecycle end to end — piloting yt-dlp (not
reimplementing it), organizing the output, and guaranteeing serviceable formats
— replacing the standalone metube deployment in ~/dev/nix-config.  The consume
side already treats yt-dlp trees as first-class (=info.json= metadata, index,
search, compat guarantees); this tree covers taking over the production side.

Prior art to absorb from =nixos-modules/metube.nix= in ~/dev/nix-config: the
=YTDL_OPTIONS= set (=writeinfojson=, =writethumbnail=, the =ejs:github= remote
component), the compat-copy postprocessor (which Loku's derivation worker now
subsumes — downloads can transcode locally instead of double-downloading), and
the =bgutil-pot= sidecar that provides PO tokens for YouTube bot checks.

** TODO Pilot yt-dlp for one-off downloads

A download endpoint + queue inside loku-server: accept a URL, run yt-dlp with
the sidecar-writing options into the downloads library, surface progress and
failures in the UI.  Serial execution, same worker discipline as compat
derivation (=.part= staging is native to yt-dlp; the watcher already ignores
it).  The bgutil-pot integration rides along as configuration.

** TODO Channel subscriptions with serial-paced check-ins

Track channels/playlists, check for new items on a schedule, and download at a
deliberately serial pace to stay friendly to would-be rate limiting.  Not MVP;
the one-off endpoint comes first.

** TODO Retire metube in ~/dev/nix-config

Once the download endpoint covers daily use: remove the metube module, host

** TODO Set an explicit crane pname/version so builds stop warning on the nameless workspace root

crane warns that the root =Cargo.toml= has no =name= during =nix build=.  The
root is a virtual workspace (=[workspace]= with no =[package]=, which is

The durable fix is in rust-template, which generates this flake, and is tracked
at [[https://github.com/LoganBarnett/rust-template/issues/64]] (emit an explicit
crane =pname=/=version= plus a compliance check); it will arrive here on a
compliance sync.  To silence it sooner, the interim is to set =pname= and
=version= on =commonArgs= in =flake.nix= locally.

** TODO Drop the local musl toolchain shim once mkMuslPackages provides one

The static musl release variant needs a musl C toolchain for any C in the
dependency tree (the bundled SQLite was the first), or the =cc= crate falls back
to the host glibc compiler and the link dies on fortify and large-file symbols
musl never provides.  rust-template's =mkMuslPackages= sets the target and
=+crt-static= but no compiler, so =flake.nix= here carries an interim
=muslCommonArgs= overlay setting the target-scoped =CC= from =pkgsCross=, passed
only to the musl builds so the cross toolchain stays out of every other build's
closure.

The durable fix is tracked at
[[https://github.com/LoganBarnett/rust-template/issues/94]]; when it lands via
compliance sync, delete the local overlay and pass plain =commonArgs= to
=mkMuslPackages= again.

** TODO Drop the local zig archiver shim once the zig helpers set =AR= themselves

The zig-cross release variants (=-gnu= portable glibc and both darwin cross
builds) drive C compiles through =cargo zigbuild=, whose binary exports an
=AR_<target>= wrapper under the per-derivation =$HOME/.cache= unless one is
already set, while crane's deps step first runs a plain =cargo check= with it
unset.  The =cc= crate marks =AR_<target>= rerun-if-env-changed, so the drift
re-runs every C build script into the same =OUT_DIR= — fatal for

run copied.  rust-template's helpers pre-set =CC=/=CXX= to stable store-path
wrappers but not =AR=, so =flake.nix= here carries an interim
=zigCrossCommonArgs= overlay pinning =AR_<target>= to a =cargo-zigbuild zig ar=
wrapper for both helpers.

The durable fix is tracked at
[[https://github.com/LoganBarnett/rust-template/issues/95]]; when it lands via
compliance sync, delete the overlay and pass plain =commonArgs= to
=mkGnuPortablePackages= and =mkDarwinCrossPackages= again.
